# 위협 모델과 보장 경계

Kechap은 보호된 작업에 필요한 검증을 설치하고 운영하는 레이어다. 공급자를 여러 개 돌린다는 사실만으로 보안이 높아지지 않는다. 로테이션이 가장 약한 공급자로의 우회 경로가 되지 않는지가 핵심이다.

## 자산과 신뢰 경계

보호 대상은 가입·로그인·게시·보상 지급 같은 제품 서버의 작업, 공급자 비밀키, 세션 무결성, 검증 결과, 사용자 개인정보다. 브라우저와 브라우저가 보낸 성공 여부·시간·이벤트는 신뢰하지 않는다. 카탈로그 기여자와 에이전트 출력도 검토 전에는 신뢰하지 않는다. 외부 공급자와 패키지에는 공급망 위험이 있다.

| 공격/실패 | 필요한 방어 | 남는 한계 |
| --- | --- | --- |
| 클라이언트의 성공 선언 위조 | 서버에서 공급자 응답 또는 replay 검증 | 공급자 판단 자체의 오류 |
| 토큰 재사용·동시 제출 | 짧은 TTL, 원자적 일회용 소비, 작업 결속 | 분산 저장소 장애 정책 필요 |
| 다른 사이트·작업 토큰 사용 | sitekey/hostname/action/세션 결속 | 공급자별 제공 필드 차이 |
| 검증 중 공급자 변경 | 발급 시 공급자 고정, 서버 저장 상태 사용 | 발급 후 공급자 장애는 재발급 필요 |
| 약한 공급자로 강제 fallback | 보장 범주·하한 고정, 서버 허용목록 | 어떤 후보도 없으면 UX 손실 |
| SSRF·비밀 유출 | 검증 endpoint 고정, 사용자 URL 실행 금지, 로그 마스킹 | 공급망 및 서버 침해는 별도 대응 |
| 과도한 challenge 발급 | 제품별 rate limit, 만료·저장 한도 | 분산 공격과 공유망 오탐 |
| 해석 가능한 고정 게임 자동화 | seed 변화, 서버 replay, 통제된 자동화 평가 | 고도화된 에이전트도 규칙을 수행 가능 |
| 실제 인간 대행·사기 | 별도 fraud·지급 정책과 사후 탐지 | CAPTCHA 단독 해결 불가 |
| biometric 강요·보관 | 명시적 동의, 최소 수집, 대체 경로, 짧은 보관 | 관할법·벤더 정책 검토 필요 |
| 접근성으로 인한 배제 | 키보드 경로, 시간 조정, 비퍼즐 대체 경로 | 하나의 게임으로 모두 대응 불가 |

## 기본 안전 조건

1. 공급자 키는 서버 환경에서만 읽고 브라우저·MCP 응답·진단 로그에 넣지 않는다.
2. origin은 서버 설정에서 허용한다. 요청의 Origin 헤더 하나만으로 보안을 보장하지 않는다.
3. 검증 오류와 timeout을 성공으로 바꾸지 않는다. 에러와 미통과를 운영 지표에서 구분한다.
4. 성공 결과는 필요한 action에만 사용하고 제품 서버가 보호 작업을 수행할 때 소비한다.
5. 저장소의 일회성 검증은 동시 요청 테스트가 필요하다. 단순 읽기 후 삭제는 원자적이지 않다.
6. 통계 로그는 토큰·원본 영상·음성·IP의 무기한 저장 없이 집계한다. 디버그 모드에도 보관 기한을 둔다.
7. 개발용 공급자·공개 테스트 키·toy PoW·가짜 verifier를 production 추천에 섞지 않는다.
8. 공급자 건강 확인은 검증 보장과 별개다. HTTP 200은 올바른 검증 응답이 아니다.

## 주장하지 않는 것

Turnstile은 challenge별 cData를 widget에 전달하고 반환 cdata를 검사합니다. hCaptcha/classic reCAPTCHA는 동일 site/action에서 얻은 bearer proof를 전달할 수 있으므로 원래 브라우저 세션의 출처까지 증명하지 못합니다. 로컬 attestation의 tenant/action/subject 결속과 공급자 원본 토큰의 출처 결속은 별개입니다.

PoW는 연산을 지불했음을 보여준다. CAPTCHA 또는 게임 성공은 지정한 과제를 수행했음을 보여준다. passkey는 계정 인증 수단이다. 이 중 어느 하나도 단독으로 실제 인간의 현재 존재, 선의, 실명 본인, 유일한 한 사람을 모두 증명하지 않는다.

타사 운영 사이트를 공격하거나 CAPTCHA를 대행 해제하는 도구는 벤치마크 범위가 아니다. 공격 실험은 자체 challenge, 소유 테스트 사이트, 명시적으로 허가받은 공급자 sandbox에서만 수행한다. 공개 보고서는 우회 코드를 제품 사이트 대상 자동화로 확장하지 않는다.

## 보안 출시에 필요한 확인

단위·계약 테스트 외에 만료 직전/직후, 동일 토큰 병렬 검증, 다른 action, 잘못된 공급자, 공급자 장애, 잘못된 JSON, oversized 응답, 접근성 fallback downgrade를 확인한다. 리버스 프록시와 다중 인스턴스 배포에서 동일 조건을 확인한 뒤 배포 지원을 선언한다. 취약점 신고 채널과 의존성 업데이트 담당자를 문서화한다.
